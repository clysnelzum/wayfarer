# LinkedIn web upstream notes

These observations are from ordinary navigation in an authenticated Chrome session. They are not an exhaustive API catalog or a promise that internal endpoints are stable. No credential values or personal response bodies are recorded here.

## Formats

- Document navigations: `text/html`.
- Voyager: `GET /voyager/api/graphql` with `queryId` and `variables`; `GET /voyager/api/me` returned normalized JSON with `data` and `included`. The media type observed on these reads was `application/vnd.linkedin.normalized+json+2.1`. Voyager is not the only source behind the current UI.
- Flagship Web: inspected component requests sent `application/json` and replied with `application/octet-stream`. Some response bodies contained React Server Component serialization; not every action response was shown to use that representation.
- A read-like presence lookup used `POST /voyager/api/messaging/dash/presenceStatuses` with `application/x-www-form-urlencoded`. HTTP method alone does not establish whether an action writes state.

## Job search alert state

The observed Spanish search layout displays `Recibir alertas de empleo para esta búsqueda`. Its native switch sits under a `JobSearchAlertToggleRef_…` component. An Easy Apply filter changed the component's suffix while pagination alone did not; Wayfarer does not derive an alert ID from it. The extractor reads only the visible switch's Boolean state. Both a filtered search and an unfiltered second page rendered an unchecked switch; a separate empty filtered second page rendered no switch. The extractor never toggles the control.

## Job search facets and filter autocomplete

The current search layout accepts `geoId` for a geography, `f_C` for a company ID, and `f_TPR` for date (`r86400`, `r604800`, `r2592000`). Changing workplace, experience, or employment type in the UI populated **`f_SAL`**, not a separate parameter per category. Observed groups are `225001` (workplace), `227001` (experience), and `226001` (employment type). Within a group, comma-separated values encode multiple selected options; `$` separates groups. Only traced options are exposed. For example, selecting Remote and Hybrid with Full-time yielded `f_SA_id_225001:272001,1621001$f_SA_id_226001:272015` after URL decoding.

Selecting two companies produced `f_C=14226,613034`; the UI preserved the organization IDs as a comma-separated value. Isolating individual selections confirmed `227001` values `278001` (Administrador), `272003` (Director), and `279001` (Ejecutivo), and `226001` value `273001` (Jornada parcial). The quick filters Easy Apply, In My Network, Verified, and Under 10 Applicants were traced to `f_AL=true`, `f_JIYN=true`, `f_VJ=true`, and `f_EA=true`, respectively.

Dynamic suggestions in the search toolbar have visible checkbox labels but no IDs on the input elements. In the observed layout, the checkbox's mounted SDUI Boolean binding ends with `JobSearchResultsPage_SemanticDynamicSuggestionPillSelectBindingKey_<group>:<value>`. The extractor reads the binding from a bounded set of React ancestors, without clicking or executing actions, and reads the checked state from the input. Only observed groups are exposed: `230001` (topics) and `228001` (industries). Selecting `AWS` in a DevOps search produced `f_SA_id_230001:277008`; selecting UX, UI, and Juegos for Product Designer produced `f_SA_id_230001:275014,272014$f_SA_id_228001:288003`. In both cases `keywords` was unchanged. These are query-specific suggestions, not a static list. The same toolbar was observed in a 390-pixel mobile viewport. Checkbox labels can be present before React attaches the bindings, so the search extractor briefly waits for hydration without requiring facet metadata for a successful search. An unrecognized binding or missing toolbar does not prevent ordinary search results from being returned.

The job search company picker sends the `com.linkedin.sdui.search.filters.requests.FiltersCompanyTypeaheadRequest` Flagship action. Its rendered options do not expose numeric IDs. `/v1/jobs/companies` opens the picker in a temporary tab after the fixed landing search selects its initial job. Opening the panel earlier can lose it during navigation, especially in a background tab. The adapter observes only the response to the typed query; it does not replay the action or click a suggestion. The response is `application/octet-stream` RSC. In the observed layout, the replacement `LazyColumn` contains ordered `TypeaheadItem` rows, each with display text and a company filter binding containing the organization ID. The adapter decodes only that response structure and never executes actions from the payload. A recognized empty column returns an empty list; an unknown response shape fails as an upstream error.

Autocomplete opens the native search location editor and reads the normal suggestion links with origin `JOB_SEARCH_PAGE_LOCATION_AUTOCOMPLETE`. Each link contains its numeric `geoId`. Example: the Buenos Aires autocomplete returned `101279968` for the province and `90009870` for the metro area. Recent locations are not returned as matches and a suggestion is not selected or applied.

A search for Remote, Past Week, and a selected company displayed an explicit no-exact-matches notice and alternative Hybrid positions. The proxy surfaces the notice as `broadened` and does not discard alternatives or certify perfect matches on responses without the notice. The search result header can display exact totals or a lower bound such as `Más de 99 resultados`; the response preserves that qualifier.

## Job detail mapping

The header and About the Job module provide different pieces. The header exposes company link/slug, plain-text location, relative publication date, fixed labels for workplace and employment type, and the call-to-action. In the inspected routes, an external Apply link was labeled as an employer-site action, while Easy Apply was a button. The adapter does not open either. Numeric labels distinguish applying-platform counts from clicks on the external button. A closed posting can retain its original description and a separate `Solicitud enviada` status for the signed-in viewer. Related jobs are collected from the `Más empleos` section and deduplicated.

The separate Job Tracker was observed at `/jobs-tracker/`, with stage changes such as `?stage=applied`, `?stage=saved`, `?stage=interview`, and `?stage=archived`. The applied view includes posting links and stage labels. It is not exposed yet: list completeness, stage transitions and pagination need separate mapping. Notes and contacts on the tracker were not read into the proxy.

## Job home pagination

The job home page appends modules to `JobsHomeFeedModuleListCollection`, a server-driven `LazyColumn`. Scrolling past the initial panels loaded a separate recent-search module and a third recommendations panel. The scroll triggered `POST /flagship-web/rsc-action/actions/pagination` with operation `com.linkedin.sdui.pagers.jobseeker.jobsHomeFeedModuleList`. The adapter lets the page issue this action itself, collects only parseable job cards, and does not click recent searches or section `Show all` links. Chrome's default hidden tab can scroll without triggering the pagination action; expanded requests enable CDP focus emulation on the temporary tab so visibility-dependent loading can run without bringing Chrome forward. A quiet scroll boundary is not proof that the personalized catalogue is exhausted.

The preferences and profile-match sections expose native `Show all` links carrying `keywords`, `geoId`, `origin`, and `originToLandingJobPostings`. Clicking the profile-match link returned two postings in one observation; opening just the same keywords and geography in a separate tab returned eleven. The preferences link accepted a comma-separated `geoId` list. Clicking its Next button retained the canonical `PREFERENCES_LANDING` origin and geographies, added `start=25`, and removed the first-page seed posting IDs. Wayfarer resolves the supported links afresh from the signed-in home page, does not return the seed context, and validates the actual navigation. A later home snapshot showed preferences and recent searches but no profile-match section, so the latter is optional rather than a permanent search preset.

## Job card labels

Searches in the United States displayed compensation labels such as `180K USD/yr - 225K USD/yr`, benefit summaries such as `Prestación de servicios médicos`, and network labels such as `5 antiguos alumnos trabajan aquí`. The adapter preserves recognized labels as localized text, not normalized compensation, benefit coverage, or employment status. When no relevant label is recognized, the corresponding field is omitted.

## Job search pagination

The legacy `/jobs/search/` route redirected to the Flagship `/jobs/search-results` layout in the authenticated session. A trial with `sortBy=DD` retained the query key but exposed no sort control in the toolbar. A subsequent comparison returned the same first 25 IDs in the same order with and without `sortBy=DD`; a page-two request dropped the parameter. URL retention alone is not evidence of sort behavior, so no sort parameter is exposed. Loading the search URL without `keywords` did not render listing cards in the observed session, with or without location and workplace filters. The observed keyword typeahead action, `com.linkedin.sdui.jobseeker.requests.keywordTypeaheadRequestAction`, rendered only the typed text in the option list for the test queries; it is not exposed as an autocomplete API.

Using the search UI's Next button changed `start` to `25` and triggered a `POST` to `/flagship-web/jobs/search-results/`. Fresh navigations to the search route with offsets `0`, `25`, and `50` yielded pages 1, 2, and 3, each with 25 distinct cards and a different first job. The search UI also sets `currentJobId` when selecting the first result; it is not necessary for opening a specific result page. Wayfarer maps a one-based page to the observed offset, checks the active page indicator when present, and derives `has_more` from the enabled Next control. Duplicate cards exposed by responsive layouts are deduplicated by job ID.

## Feed pagination and card mapping

The inspected layout virtualizes cards inside the feed's own scrolling container; the document itself may have no scroll range. Scrolling to the bottom reveals a distinct `Load more` / `Cargar más` control outside individual cards. Activating it issued `POST /flagship-web/rsc-action/actions/pagination` with the operation `com.linkedin.sdui.pagers.feed.mainFeed`, a JSON request, and an `application/octet-stream` response with RSC markers. In one trace, five new cards appeared after a click. This is a read-side UI action; Wayfarer leaves the choice of feed sorting in Chrome.

Wayfarer retains cards once mounted, deduplicates by the opaque card key, and advances by less than a viewport per step. It uses a bounded time and load budget rather than promising a fixed number of posts or serializing LinkedIn's internal continuation state. Evidence of an enabled control or surplus collected items is reported separately as `has_more`. No raw request payload or cursor is exposed.

Observed card fields: the post body appears in `expandable-text-box`; profile/company links in the header identify the author in the tested layout; relative time is visible text; hashtags and media have separate markup. On the compact layout, exact counts were associated with the reaction, comment, and repost buttons via their icon IDs. Values are omitted when the parser cannot identify the corresponding field or when the count is abbreviated. This mapping does not yet cover absolute timestamps, every post attachment type, nested reposts, comment threads, or a canonical permalink for cards without a visible link. `Destacados` and `Recientes` were observed in the sort menu; switching the account's preference was not tested.

## Personal and company profile mapping

On personal profiles (`/in/{slug}/`), the observed SDUI layout renders inside a scrollable `main#workspace` container (the document root itself may not be the active scroller). Below-the-fold profile cards (`[id^="profileCards"]`, `[componentkey^="profileCards"]`, `[id*="lazy_anchor"]`, and `[componentkey^="com.linkedin.sdui.profile.card.ref"]`) can mount as empty placeholders until scrolled into view. Because Chrome does not hydrate visibility-dependent lazy SDUI cards in an unfocused background tab by default, personal profiles (along with expanded `/v1/jobs?limit=...` recommendations and `profile_match` source resolution) use `ReadRendered` in `internal/chrome/browser.go`, which enables `Emulation.setFocusEmulationEnabled` and `Emulation.setDeviceMetricsOverride` (`1280×900`, `deviceScaleFactor: 1`, non-mobile) scoped to the temporary tab with a `90s` timeout.

In `internal/linkedin/profile.js`, the extractor walks all scrollable workspace and ancestor containers (`main#workspace` fallback) and scrolls in bounded passes (up to 14 steps within a 5500 ms pass deadline, falling back to `scrollIntoView` on remaining empty placeholders). It re-queries `main` and the top card after awaits in case React hydration replaces the root DOM nodes, resets scrollers back to the top once core sections mount after a pre-core scroll pass (or while waiting for core sections within a 75000 ms hydration budget), and keeps polling until placeholders hydrate or settle. Sections are matched by SDUI component keys (`com.linkedin.sdui.profile.card.ref*Topcard`, `*About`, `*Activity`, `*Featured`, `*ExperienceTopLevelSection`, `*EducationTopLevelSection`, `*CertificationTopLevel`, `*Skills`, `*LanguageTopLevel`, `*Projects`, `*VolunteerExperienceTopLevel`, `*PublicationTopLevelSection`, `*HonorsTopLevel`, `*RecommendationsTopLevel`, `ProfileNullStateCardAnchor_*`) with Spanish/English heading fallbacks. Collection rows use `[componentkey^="entity-collection-item-"]` (including nested sub-items for multi-role experience entries at one company). Truncated lists that require navigating to `/details/*` sub-routes are not traversed.

On company About pages (`/company/{slug}/about/`), `section.org-top-card` carries the tagline, verified/premium indicators, logo/cover image URLs, follower/employee labels, and fallback industry/headquarters items. In the Overview `<dl>`, `Tamaño de la empresa` / `Company size` can have multiple `<dd>` siblings: one for the employee-range string and another linking to associated members; links to `/search/results/people/` expose the numeric `currentCompany` organization ID. Separate sections provide workplace policy (`section[data-view-name="org-member-about-workplace-policy"]` or `data-scroll-to-selector="workplace-policy"`), commitments (`section[data-view-name^="org-member-commitment-"]`, preferring `.org-commitment-description__body` / `[class*="commitment-description__body"]` over generic `<p>` elements so nested action/report labels are excluded), and locations (`.org-locations-module__card-spacing` / `.org-location-card`, supplemented by embedded `code[id^="bpr-guid-"]` `groupedLocations` and `followerCount` payloads when present, including normalized `urn:li:fsd_followingState:...` entity resolution). Sidebar cards (`aside .artdeco-card, aside section`) expose affiliated/showcase pages and similar pages.

## Adapter choice and open work

The current adapter lets Chrome execute the site's normal page loads over a shared persistent browser-level CDP WebSocket (`internal/chrome/cdp.go`, `internal/chrome/browser.go`), then maps the rendered results to Wayfarer's own JSON models. The transport multiplexes concurrent flattened target sessions by command ID over one read loop with serialized writes (capped at two concurrent tab slots) and shares the initial dial handshake so canceling one HTTP caller does not interrupt other callers or tear down the connection. It does not implement the internal Voyager or Flagship wire protocol. This keeps the first version usable across two upstream formats without requiring raw credential handling. It also means some source fields are not available and the extraction can break when the page changes.

Next research tasks: map stable cross-request feed continuation, canonical post IDs, and expanded comment and attachment schemas; map remaining job facet surfaces and alternate layouts; identify which responses contain recommendation cards and feed posts; evaluate `/details/*` sub-routes for truncated personal profile lists; compare rendered field coverage against direct response schemas. Messaging is out of scope. Keep future adapters behind the existing Go interfaces and verify schema changes against sanitized fixtures.
